Business model decisions, target customer analysis, codebase changes required

1. Business Model Overview

Core Value Proposition Wholesale-quality spices & dry fruits delivered to B2B customers' doorsteps. Shuddhidham keeps 13% margin on best-available wholesale price, with no need for customers to travel to Asan/Kalimati.

How It Works

  • Procurement on Demand — No large pre-stock. Order comes in, goods are sourced same/next day from the wholesale market.
  • Buffer stock only — 2–3 cases of fast-moving SKUs kept on hand at any time.
  • Agent-first channel — Sales agents walk routes (restaurant belts, sweet shop lanes, puja corridors) to onboard and collect orders. App is for reorders once trust is established.
  • Delivery to doorstep — The agent or delivery person delivers after sourcing. Payment collected on delivery or settled later.
  • Margin model — 13% on top of the lowest wholesale price. Must source right every time.

Business Stage Constraints

  • Small team — agents double as collectors.
  • Limited storage — no warehouse, only buffer cases.
  • Reputation is fragile — first 2–3 months matter most for trust.
  • Cash flow is king — credit must be managed carefully.
  • Procurement intelligence matters from day one — which SKUs move fastest drives better sourcing deals.

Order-to-Cash Flow (Procurement on Demand)

CREDIT ENTRY Agent creates order as credit in POS
→
ADMIN REVIEWS Sees combined open credits → sources accordingly
→
SOURCING Buys from Kalimati / Asan at best price
→
DELIVERY Agent or driver delivers to customer
→
PAYMENT CLOSED RecordPayment → credit converts to Sale

3. What's Already Built (No Changes Needed)

Foundation is solid The core flows required for the procurement-on-demand model are already implemented. The work is refinement, not rebuilding.
  • ✓
    Credit / Preorder System
    Sale created with payment_method='credit' → payment_status='unpaid' → CustomerLedgerEntry with pending debit. This IS the preorder mechanism.
  • ✓
    RecordPayment Page
    Agent or admin can record payment against outstanding balance. FIFO allocation against pending invoices. Closes the credit loop.
  • ✓
    CustomerLedgerEntry & Report
    Full ledger with aging buckets (current / 1-30 / 31-60 / 61-90 / 90+ days). Shows open credits in real time. This is the admin's pipeline view.
  • ✓
    Sales Agent System
    SalesAgent model with territory, commission tiers (retail % and wholesale profit %), SalesAgentLedger for earnings tracking, AgentEarningsSettlement dashboard.
  • ✓
    Inventory / Stock Tracking (Admin)
    StockLevel, InventoryMovement, ProductBatch with FIFO. Low stock alerts via AlertRule. InventoryList, StockAdjustment, InventoryAuditLog pages. InventoryService centralizes all changes.
  • ✓
    Demand Pattern Data from Day 1
    Every sale (including credits) creates SaleItems. Sales Report + InventoryTurnover Report can show fast-movers from first sale. This data drives sourcing decisions.
  • ✓
    WhatsApp Receipt on Sale Completion
    PDF invoice generated and sent via WhatsApp after sale. Builds trust with B2B customers immediately.
  • ✓
    Wholesale / Retail Order Channels
    Sale.order_channel distinguishes wholesale vs retail. Commission calculations differ per channel. Ready for when you formalize B2B pricing tiers.
  • ✓
    Commission Auto-posted on Payment
    Sale model observer: when payment_status changes to 'paid', commission is auto-posted to SalesAgentLedger. Agent only earns on collected orders.
  • ✓
    Multi-session Cart (POS)
    POS supports multiple simultaneous sessions. Agent can hold one customer's order while starting another. Useful for agents serving multiple walk-in orders.

4. Required Codebase Changes

Principle The POS must be free from stock enforcement since the model is procurement-on-demand. Inventory tracking stays active for the admin only. Sales figures should reflect real money received — credits are a separate pipeline.

① Remove Stock Enforcement from POS

HIGH PRIORITY POS EnhancedPOS.php

Currently the POS blocks adding items to cart and updating quantities when availableStock < requested quantity. This is wrong for a procurement-on-demand model where agents take orders before sourcing.

What to do: Remove or bypass the stock check in addToCart() and updateQuantity(). Keep the stock display (show available qty) but don't block the action.

// app/Filament/Pages/EnhancedPOS.php // IN addToCart() — REMOVE this block: if ($availableStock < $totalNeeded) { Notification::make() ->warning() ->title('Insufficient Stock') ->body("Available: {$availableStock}, ...") ->send(); return; // <-- remove this guard } // IN updateQuantity() — REMOVE this block: if ($availableStock < $quantity) { Notification::make() ->warning() ->title('Insufficient Stock') ->send(); return; // <-- remove this guard } // KEEP: Still show availableStock in search // results for informational purposes only.

File: app/Filament/Pages/EnhancedPOS.php
Lines: ~887 (addToCart block), ~990 (updateQuantity block)

② Sales Report: Show Only Paid Sales

HIGH PRIORITY Reports SalesReport.php

Currently the Sales Report filters by status = 'completed' only. This includes credit (unpaid) sales in the revenue totals — money not yet received.

Decision from chat: "Only completed payments show as sales. Credits stay as credits until closed." Sales = real money in.

// app/Filament/Pages/SalesReport.php // In getSalesData() and getSalesByPaymentMethod(): $query = Sale::query() ->whereBetween('date', [...]) ->where('status', 'completed') ->where('payment_status', 'paid'); // <-- ADD THIS // Apply same filter consistently to ALL // metric queries in this file.

File: app/Filament/Pages/SalesReport.php
Affects: getSalesData(), getSalesByPaymentMethod(), top products query

③ Add "Open Orders" Dashboard for Admin

HIGH PRIORITY Admin New widget or existing CustomerLedger

Admin needs a real-time view of all open credit sales (pending orders) aggregated by product. This is the sourcing intelligence: "Three agents created credits for turmeric today — source 10kg."

Option A (quick win): Use the existing CustomerLedgerReport page — filter by status='pending' to see all open orders. Already built.

Option B (better): Add a Filament widget on the admin dashboard showing open credits grouped by product variant (SaleItems of unpaid Sales). This gives sourcing summary in one view.

// Option B: New widget query concept SaleItem::query() ->join('sales', 'sale_items.sale_id', '=', 'sales.id') ->where('sales.payment_status', 'unpaid') ->where('sales.status', 'completed') ->groupBy('sale_items.product_variant_id') ->select([ 'product_variant_id', DB::raw('SUM(quantity) as total_ordered'), DB::raw('COUNT(DISTINCT sales.customer_id) as customer_count') ]) ->with('productVariant.product') ->get();

This is the operator's sourcing dashboard. Start with Option A (no code needed), graduate to Option B when the pattern is clear.

④ Agent Role: Hide Inventory Navigation

MEDIUM PRIORITY Permissions Roles & Permissions

Sales agents should only see: POS, their earnings, customer ledger for their customers, and price list. They should NOT see inventory pages, stock reports, purchase orders, or supplier data.

What to do: Ensure the agent role does NOT have these permissions:

// Permissions to EXCLUDE from Agent role: view_inventory manage_inventory view_stock_reports view_stock_valuation view_inventory_audit manage_purchases view_supplier_ledger view_profit_reports manage_products manage_categories // Permissions agents SHOULD have: access_pos_billing view_customers view_price_list view_agent_earnings (their own only)

Configure via Roles & Permissions in the admin panel. No code change needed if role system is already flexible.

⑤ completeSale: Skip FIFO Batch Check When No Stock

MEDIUM PRIORITY Services EnhancedPOS.php / InventoryService.php

Currently completeSale() calls InventoryService::decreaseStockWithBatchInfo() for every item. If buffer stock is zero (common in demand-on-demand), this may create negative stock levels or allocation errors.

What to do: Wrap the FIFO allocation in a guard — if no batch stock exists, still create the SaleItem but skip batch allocation. Record an InventoryMovement with a 'credit_sale' or 'preorder' note for reconciliation later when goods are received.

// In completeSale(), per cart item: $currentStock = InventoryService::getStock( $item['variant_id'], $storeId ); if ($currentStock > 0) { // Normal FIFO decrease $allocationResult = InventoryService ::decreaseStockWithBatchInfo(...); $primaryBatchId = $allocationResult[...]; } else { // Preorder — no stock to allocate yet $primaryBatchId = null; // Optionally: log a preorder movement }

Prevents errors when agents take orders for items not yet in buffer stock. Stock will be updated when goods arrive via Purchase Receipt.

⑥ Credit Sales: Label Clearly in POS Receipt

LOW PRIORITY UX InvoiceService / ReceiptService

When an agent creates a credit (preorder) sale, the customer's WhatsApp receipt should clearly say "ORDER CONFIRMED — Payment due on delivery" rather than looking like a paid receipt.

What to do: In the invoice/receipt template, check payment_status and conditionally show "PENDING DELIVERY" watermark or status label instead of "PAID."

// In receipt/invoice template: @if($sale->payment_status === 'unpaid') <div class="status-badge pending"> ORDER CONFIRMED <small>Payment due on delivery</small> </div> @else <div class="status-badge paid">PAID</div> @endif

5. System-Level Decisions & Rationale

Decision Choice Made Rationale
Fully detach stock from POS? Partial — Remove enforcement, keep tracking Keep inventory system active for low-stock alerts and sourcing intelligence. Only remove the blocking gate that prevents sales when stock = 0.
How to handle preorders? Use existing Credit system Payment method = 'credit' creates an unpaid sale + customer ledger entry. Already built. No new tables or flows needed.
What counts as a "Sale" in reports? Only paid (payment_status = 'paid') Revenue = money received. Credits are a pipeline/receivables view. Mixing them inflates reported revenue with unfulfilled orders.
Where does the admin see open orders? CustomerLedger (now), dedicated widget (later) CustomerLedgerReport filtered by status='pending' shows all open credits grouped by customer. A product-grouped view comes next for sourcing decisions.
Should agents track stock? No — admin only Agents need: POS, price list, customer ledger, their own earnings. Stock complexity slows them down and creates confusion since buffer stock won't match orders anyway.
Bring full inventory back when? Trigger-based — not time-based Reintroduce full stock enforcement when: (a) you pre-stock 5+ SKUs regularly, (b) you have 2+ storage locations, or (c) agent errors about availability start happening.
Loyalty program — activate now? Defer — B2B focus first Loyalty tiers/points make sense for repeat B2C. For B2B (restaurants, sweet shops), the loyalty equivalent is consistent pricing and reliable service. Don't add noise to agent UX now.
WhatsApp receipts — keep? Yes — high value for B2B trust B2B customers want paper trail for bookkeeping. WhatsApp PDF = instant receipt = trust signal. Especially important for credit sales (order confirmation).
